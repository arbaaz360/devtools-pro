# DU-03 — RegExp Tester

`text.regex` runs a single ECMAScript `RegExp` over one document in `match` or `replace` mode, reporting exact match/group offsets, a copyable text listing, and editor annotations. Its own README is candid that it is **not** ICU and does not implement whitespace/comment mode or UAX 29 word boundaries — exactly the two things the card calls out as required beyond ordinary flags — and testing confirms the replacement grammar is plain ECMAScript `$&`/`$1`-`$9`/`$<name>`, not the card's `$0` or literal-`\n`/`\t` substitution.

## Gaps to close

- **Row 1/5/8 (missing): not ICU, no `x` mode, no real UAX 29 word boundary.** These are flavor-level gaps; closing them means swapping or layering a different regex engine (or a preprocessing step for free-spacing mode and a Unicode-segmentation-based boundary check), not a fix inside the current ECMAScript-`RegExp` processor.
- **Row 10 (partial) / 13 (missing): report-expression grammar is ECMAScript-only.** `$0` and literal `\n`/`\t` interpretation would need a small preprocessing pass over `replacement` before it reaches `String.prototype.replace` (translate `$0`→`$&`, and interpreted-escape sequences → real characters) — currently the string goes to the engine unmodified.
- **Row 26 (partial): catastrophic backtracking is only contained by the host killing the worker**, not by the processor itself. If graceful, in-processor cancellation of a running match is wanted, that requires either a different (linear-time) engine or chunked/steppable matching, which the current single `matchAll`/`exec` call cannot do.

## Not covered

- Rendering: inline highlight painting, the expandable/searchable match tree, and previous/next navigation are shell UI, not observable headlessly.
- Sample/paste/clear buttons and stale-selection UI behavior while a pattern is being edited.
- Keyboard interaction and focus behavior.
- Invalid-UTF-8 byte input (the CLI harness only accepts string arguments, so `regex.invalid-utf8` was read from the source, not exercised).
