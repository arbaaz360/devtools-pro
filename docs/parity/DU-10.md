# DU-10 — UUID Generator/Decoder

`identity.uuid` generates v1/v3/v4/v5 UUIDs (single or 1–100 batch, upper/lower case) and decodes the canonical 36-character form into version, variant, raw bytes, and — for v1 — timestamp, clock sequence and node, with v1/v4 entropy drawn from injected clock/randomness services so results are reproducible. One combined operation handles both directions, switching on an explicit `mode` option or on whether the `uuid` input port carries text. Nearly every Required and Acceptance item checked is `met`; the one open question is whether "generation occurs only on explicit action" actually holds given the operation also declares `inputChange` as a trigger mode.

## Gaps to close

- **Row 20 (partial): generate-mode trigger scoping is unproven from the manifest alone.** The operation's `trigger.modes` includes `inputChange` with no mode-conditional trigger rule, so whether the shell actually suppresses auto-regeneration while `mode=generate` (as the card requires) versus only auto-triggering decode when the `uuid` port changes is a shell-wiring question this audit cannot settle headlessly. Worth a direct check against the running app, or a documented note in the manifest/README about how the shared trigger is scoped per mode.

## Not covered

- Whether the desktop shell actually withholds regeneration on unrelated input/option changes while in generate mode (tied to row 20; needs the running app, not just the manifest).
- Decoder/generator form layout, per-field copy buttons, sample-UUID button, and the detection-reset control are shell UI, not observable headlessly.
- Keyboard and selection behavior.
