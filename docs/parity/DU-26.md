# DU-26 — SQL Formatter (`format.sql`)

`format.sql` tokenizes SQL text and offers `beautify` (clause-oriented
reformatting) and `minify` (whitespace/comment stripping) across five
dialect identities, with keyword-case and comma-position controls. Standard
formatting — clause layout, comment/string handling, dialect quoting,
multiple statements and malformed input — all work as documented. Two real
defects surfaced during this audit: the `space-4` indentation choice that
the manifest itself offers silently produces 2-space output instead of 4,
and PL/SQL's procedural blocks (`BEGIN`/`IF`/`END`) are not restructured,
producing badly malformed output for exactly the dialect feature PL/SQL
support is supposed to cover.

| # | What the card requires | What the tool does | Verdict | Evidence |
|---|---|---|---|---|
| 1 | Standard SQL dialect | `dialect: "sql"` tokenizes ANSI quoting (`'…'` strings, `"…"` identifiers) | met | `--operation beautify --input "input=SELECT a,b FROM Foo WHERE x=1" --options '{}'` → clause-per-line output, `"dialect":"sql"` |
| 2 | MySQL dialect | `dialect: "mysql"` additionally accepts backtick identifiers | met | `--operation beautify --input 'input=SELECT `col` FROM `Tbl`' --options '{"dialect":"mysql"}'` → `` SELECT\n  `col`\nFROM `Tbl` `` |
| 3 | MariaDB dialect | `dialect: "mariadb"`, same backtick handling as MySQL | met | scratchpad run: `SELECT \`col\` FROM \`Tbl\`` with `dialect: mariadb` → identical formatting, `"dialect":"mariadb"` |
| 4 | PostgreSQL dialect | `dialect: "postgresql"` accepts `::` casts, `$$…$$` dollar-quoted strings as single tokens | met | scratchpad run: `SELECT $$literal $ dollar$$ FROM t` → the dollar-quoted body survives as one token, not split on the interior `$` |
| 5 | PL/SQL dialect (selection and tokenization) | `dialect: "plsql"` is selectable and tokenizes its comment/string forms | met | `--operation beautify --input 'input=SELECT 1 FROM dual; -- comment' --options '{"dialect":"plsql"}'` → `"dialect":"plsql","comments":1` |
| 6 | PL/SQL procedural blocks (`BEGIN`/`END`, `IF`/`END IF`) | The formatter has no block-aware indentation for procedural keywords; `BEGIN`, `IF`, `END IF` and `END` are emitted as ad hoc statement breaks, not nested blocks | missing | scratchpad run, `dialect: plsql`, input `CREATE OR REPLACE PROCEDURE p AS\nBEGIN\n  IF x THEN\n    SELECT 1 FROM dual;\n  END IF;\nEND;` → output is `CREATE\n  OR REPLACE PROCEDURE p AS BEGIN IF x THEN\nSELECT\n  1\nFROM dual;\n\nEND IF;\n\nEND;` — the procedure header, `BEGIN` and `IF` collapse onto one unindented line and `END IF;`/`END;` are each treated as their own top-level statement; what it would take to close: clause-keyword handling for `BEGIN`/`END`/`IF…THEN`/`END IF`/`LOOP`/`END LOOP` with block-depth indentation, analogous to the existing `SELECT`/`FROM`/`WHERE` handling |
| 7 | Uppercase or original (preserve) keyword case | `keyword-case`: `upper` (default), `lower`, `preserve` — a superset of the two named in the card | met | `--options '{"keyword-case":"preserve"}' --input "input=select a,b from Foo"` → keywords kept as typed; `--options '{"keyword-case":"lower"}' --input "input=select A from B"` → `select\n  A\nfrom B` (identifiers untouched) |
| 8 | Indentation control, 2 spaces shown in the main screenshot | `indent: "space-2"` is the default and produces 2-space indents | met | default-options beautify output above uses 2-space indents throughout |
| 9 | Retain shared indentation controls (2/4/tab) | `indent` enum offers `space-2`, `space-4`, `tab`; `tab` and the undocumented alias `"4"` correctly change the indent width, but the manifest's own `space-4` choice does not | missing | scratchpad run, `SELECT a FROM t WHERE x=1 AND y=2`: `{"indent":"space-4"}` → 2-space indent (`WHERE x = 1\n  AND y = 2`, unchanged from default); `{"indent":"4"}` → correct 4-space indent (`WHERE x = 1\n    AND y = 2`); root cause in `plugins/sql/processor.mjs:233` (and duplicated in `plugins/sql/beautifier.mjs:3`): `options.indent === 'tab' ? '\t' : (options.indent === '4' ? '    ' : '  ')` checks the literal alias `'4'`, never `'space-4'`, so selecting the dropdown's own "4 spaces" choice silently falls back to 2 spaces; what it would take to close: also match `'space-4'` (and, for symmetry, `'space-2'`) in that ternary |
| 10 | UX: source/result with dialect, keyword-case, indentation and Copy on output | Workspace binds an editor, a form with all four options, and an output component | n/a (shell) | `manifest.json` `workspaces[0].bindings` |
| 11 | Language identity follows the chosen dialect | Output artifact's declared `mime` is the fixed `text/x-sql` regardless of dialect; no per-dialect syntax-highlighting identity | n/a (shell) | `manifest.json` operation `outputs[0].mime`; whichever editor language tag the shell attaches is a presentation choice outside the processor |
| 12 | No database connection needed | Formatter is a pure text-to-text tokenizer; no network or connection code exists in the package | met | `plugins/sql/processor.mjs`, `plugins/sql/beautifier.mjs` — no `fetch`, socket or connection-string handling anywhere |
| 13 | Dialect-specific quoting | Backtick (MySQL/MariaDB), double-quoted identifiers (standard/Postgres), dollar-quoted strings (Postgres) all tokenize as single, intact tokens | met | rows 2–4 |
| 14 | Dialect-specific operators | PostgreSQL `::` cast and `\|\|` concatenation tokenize and format correctly (with the type name after `::` treated, and cased, as a keyword) | met | scratchpad run: `SELECT a::int, b \|\| c FROM t` (postgresql) → `SELECT\n  a :: INT,\n  b \|\| c\nFROM t` |
| 15 | Procedural blocks | See row 6 | missing | as row 6 |
| 16 | Comments (single-line `--`/`#`, multi-line `/* */`) | Both forms tokenize, are preserved in `beautify` output, and are counted in the `comments` property | met | `SELECT /* block comment */ a FROM t` → comment retained in place, `"comments":1`; unterminated `/* …` retained verbatim rather than crashing |
| 17 | Multiple statements | Statement boundaries (`;`) start a new formatted block; `statements` property counts them | met | `--input "input=SELECT 1; SELECT 2;"` → two `SELECT` blocks with a blank line between them, `"statements":2` |
| 18 | Incomplete queries | A query missing its final clause body formats what is present without throwing | met | `--input "input=SELECT a FROM"` → `SELECT\n  a\nFROM`, exits 0 |
| 19 | Case preservation — "original" must not lowercase identifiers | `keyword-case: "preserve"`/`"lower"` only affects recognized keywords; identifiers keep their original case in every mode | met | row 7's `keyword-case: lower` example: identifier `A`/`B` untouched while `select`/`from` lowercase |
| 20 | Minify: comments removed, whitespace collapsed, comma-separated punctuation tight | `minify` strips comments (no directive support observed) and collapses whitespace to the syntactically required minimum | met | `--operation minify --input "input=SELECT   a,   b  FROM Foo -- comment\nWHERE x = 1"` → `SELECT a,b FROM Foo WHERE x=1` |
| 21 | Comma position (`end` default / `start`) | `comma-position: "start"` moves top-level list commas to the start of the next line; it does not reach commas inside a parenthesized list (`IN (1, 2, 3)` stays comma-after) | partial | scratchpad run: `{"comma-position":"start"}`, `SELECT a, b, c FROM t` → `SELECT\n  a\n  , b\n  , c\nFROM t` (met for the top-level `SELECT` list); `SELECT a FROM t WHERE x IN (1,2,3)` with the same option → `IN (1, 2, 3)` unchanged; what it would take to close: apply the same comma-position rule inside parenthesized argument/value lists, not only top-level clause lists |

## Not covered

Syntax highlighting, the editor/result panel layout, the dialect/keyword-case/
indent/comma-position form controls themselves, and any AST-level semantic
validation (explicitly out of scope per `plugins/sql/README.md`). These are
presentation or explicitly-declared-out-of-scope concerns, not processor
behavior this audit can check headlessly.
