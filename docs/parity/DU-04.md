# DU-04 — JWT Debugger, decode/sign/verify

`security.jwt` decodes a JWS compact token into header/payload/signature and verifies it offline against a caller-supplied key for HS/RS/PS/ES 256/384/512, with `exp`/`nbf` evaluated against an injected clock, entirely with web-platform `crypto.subtle`. It covers the decode-and-verify half of the card thoroughly, with well-separated structural, key-import and signature-validity error codes — but the card's title and Required section also ask for **signing**, and the package's own README says plainly that signing, private keys and the re-signing workflow are out of scope; none of it exists.

Every `met`/`partial`/`missing` row above cites a headless command run against `plugins/`, the package README, or `manifest.json`.

## Gaps to close

- **Row 7/10/13 (missing): no signing.** This is the single largest gap against the card, which is literally titled "JWT Debugger, decode/sign/verify." Closing it needs a `sign` operation (or a `mode` option) accepting header/payload edits and a private key/secret, producing a new compact token with `crypto.subtle.sign`, plus the "derived-update origin tracking" the card asks for so an edited field doesn't silently re-sign a token the user only meant to inspect.
- **Row 6 (partial): only public keys are accepted for RS/PS/ES.** Once signing exists this needs private-key (PKCS8) import for those families too.

## Not covered

- Segmented token highlighting, the editable header/payload/key UI, sample loading, and "prominent" signature-status presentation are shell rendering, not observable headlessly.
- Detection-preference UI and its reset control.
- Whether the desktop shell actually surfaces `key-import` vs `invalid` vs `unsupported` differently to the user (the processor distinguishes them; the presentation of that distinction is unverified here).
